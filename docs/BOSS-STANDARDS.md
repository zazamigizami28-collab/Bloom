# Bloom ボス実装基準
2026-09-24制定。ユーザー提供のボス設計論を、Bloom向けの作業手順へ要約・翻案したもの。
目的は「負けた理由が分かり、次に試す行動を思いつける戦闘」を作ること。
新ボス着手時は本書→BOSS-DEVELOPMENT-GUIDE.md→最新AUDITの順に必要箇所を読む。

## 0. 適用範囲と優先順位
最新のユーザー指示 > 最新版の採用仕様 > 本書の推奨値。既存のHRT-01を本書へ合わせて勝手に作り直さない。
BloomはPC向け2D・1対1・パリィ中心。スタミナ、DPSチェック、雑魚召喚、3Dロックオン、部位破壊を追加する指示ではない。
一般論に含まれる実在作品への評価は検証していないため、根拠や断定として転記しない。

## 1. 作る前に一文で目的を決める
「この園芸機械は、○○を観察し、△△を選ぶ力を試す」と書く。
主目的は基礎の確認、新しい判断の導入、エリアの感情的な締めのいずれか一つ。副目的は主目的を邪魔しない範囲。
初見の仕組みを覚える時間を与える。HP増量、火力増加、長い連撃だけで難しくしない。
機械本来の用途（給水、剪定、運搬など）から武器・構え・射程・移動を説明できるようにする。

## 2. 攻撃を表にしてからAIを書く
各行動に次を記録する。空欄のまま実装を始めない。
| 項目 | 記入内容 |
| --- | --- |
| 名前・役割 | 園芸機械らしい動作と、何を判断させる攻撃か |
| 使用条件 | 距離、向き、前行動、形態、連発制限 |
| 時系列 | 構え、点灯、白化、合図音、方向固定、各段命中、有効終了、次の構え |
| 範囲 | 見た目と判定の位置・幅・高さ、移動/射出の速度 |
| 対処 | 通常パリィ、特殊パリィ、ローリング、距離回避の可否 |
| 報酬 | 反撃可能回数、成長機会、回復可否、BREAK値 |
| 第二形態 | 学んだ対処をどう応用するか、追加判断は何か |

完全ランダムは禁止。距離や直前の行動を条件にし、連続で対処困難な攻撃が出ない制限を持つ。
行動選択後に都合よく別技へ差し替えない。向きの追従終了も明示する。
背後対策は毎回ではなく、間隔や機会数で制限。水は通常攻撃と混ぜ、遠方で育成だけ待つ戦法の強さを確認する。

## 3. 反撃窓と回復窓を分ける
各攻撃の最後に「まだ連撃中か、終わったか」が分かる姿勢・音を作る。
反撃窓は、最終有効判定の終了から次の脅威まで。移動時間、武器の発生と硬直まで含めて1〜2回攻撃できるか実測する。
短い隙の技も可。ただし一連の戦闘に明確な長い隙を置く。全攻撃を同じ間隔にしない。
回復は1.2秒必要。安全地点への移動も含めて完了できる機会を設計し、全コンボ後に必ず回復できるという意味にはしない。
「回復窓がある」はデータ上の休止時間だけで判断せず、実際の操作で確認する。

## 4. 視認性・予兆・判定
2Dではプレイヤー、危険部位、弾、赤い予兆が画面内で読めることを優先する。画面端・密着・裏側・最大伸長で確認。
巨大機械の全身が映っていても、刃先が隠れていれば不合格。HUD、白点滅、花びら、揺れとの重なりも確認する。
現行基準は点灯480ms前、白化240ms前、合図音/方向固定160ms前、受付180ms/ジャスト60ms。
初点灯や白化を「即パリィ」と教えない。射出の合図と着弾時パリィは別。構えは技の種類を教え、最終合図はタイミングを教える。
赤はパリィ不可であることを色以外の構え・音でも伝える。HRT-01では高枝最終段だけ。次ボスの赤頻度は個別に設計する。
判定は可視の危険範囲からはみ出させない。見た目より5〜10%小さい判定は調整候補であって一律適用しない。軌跡の装飾と危険範囲を区別し、デバッグ表示と左右・上下・高速フレームで照合する。
無音でも対処可能にする。音だけに依存した画面外攻撃を作らない。

## 5. 第二形態は判断を一つ増やす
HP等の明確な条件で一度だけ移行。演出中の無敵、入力制限、残弾・攻撃の清掃、終了後の予備動作をセットにする。
最初の新技は仕組みを観察できる余裕を持たせる。既存技の意味を失わせず、距離、追加段、攻め時など判断を一つ増やす。
単なる高速化・威力増加だけにしない。ただし勝利条件や操作体系そのものを必ず変える必要はない。
強制ノックバックや新カメラは必須ではなく、既存配置と安全な移行で成立するなら追加しない。

## 6. テストしてから難易度を決める
| 観測 | 記録すること |
| --- | --- |
| 敗因の理解 | どの攻撃で、どう操作して失敗したと本人が説明したか |
| 学習 | 1回目と3回目の成功パリィ、回避、到達形態、攻め時の理解 |
| 公平性 | 画面端、裏側、予兆の遮蔽、見た目と判定の食い違い |
| 戦略 | 裏回り連打、遠距離待ち、特定技待ちだけが有利すぎないか |
| テンポ | 戦闘時間、待ち時間、回復機会、成長頻度、再挑戦の待ち |
| 意欲 | 次に何を変えて試したいか、もう一度挑みたいか |

3回目で必ず長生きすることを合否条件にしない。挑戦行動の変化や理解も見る。単発の反応や短い生存時間だけで設計不良と断定しない。
遮蔽・揺れ等が怪しければ有/無の比較で原因を切り分ける。「弱いボスの証拠」と断定せず、要素の寄与を測る。雑魚や3DカメラはBloomへ持ち込まない。
修正順は説明/予兆/判定の整合→行動選択/隙→難易度数値。ユーザー評価済みの部分を重複修正しない。

## 7. 完了判定と保存
- 攻撃表、実装、表示、説明が一致。
- 通常/特殊/不可、連発制限、資源機会、反撃窓/回復窓を検証。
- 形態移行、BREAK、被撃、休止、敗北、再戦、画面切替で状態が残らない。
- npm run check成功と実機評価を別記。描画スタブを視認性や聴感の確認と呼ばない。
- 実装済み、未実装、撤回、評価待ちをAUDIT/CHANGELOGに分ける。
- 変更前後を別コミットにし、GitHub保存と公開ソースの一致を確認する。

## 次回AIへの作業指示テンプレート
1. 最新版/ユーザー評価/本書と既存ガイドを確認し、既に解決済みの課題を除外する。
2. ボスの主目的を一文、機械の用途、攻撃表、形態差、想定反撃/回復窓を書く。
3. 既存入力・判定・花モデルを再利用し、ボス定義と表示を分離して実装する。
4. 境界回帰と実機確認表を作る。新しいボスだからといってプレイヤー受付や成長速度を勝手に変えない。
5. 評価から必要な箇所だけ調整し、監査・変更履歴・GitHub保存・公開を完了する。
