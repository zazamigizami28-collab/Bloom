# 次ボス開発の手順とノウハウ
基準: HRT-01 v0.6.11。仕様の根拠はHRT-01-RETROSPECTIVE.mdと版別AUDIT。既存ボスの丸写しで機能数を増やすのではなく、新ボスの戦い方を一つ決める。

## 1. 機械の用途から攻撃を作る
給水/剪定など本来の仕事を、構え・発射口・攻撃範囲へつなげる。水も肥料も同じモーションにしない。初見で種類が分かる形状と色を使い、色だけに依存しない。

## 2. 攻撃仕様を表にしてから実装
各技について、用途、使用距離、構え、段ごとの時刻、方向固定、判定範囲、通常/特殊/不可、回避方法、終了後の隙、第二形態差分を記入する。段数よりリズム差を優先する。例: 横薙ぎは360msの二連後1200ms溜め、短枝は460ms後880ms。速さを上げる前に構えと合図を読めるか評価する。

## 3. 予兆は一つの時計で処理
telegraph.tsを共有。光は発生480ms前→240ms前白化→0で消灯。音/方向固定は160ms前。白化240ms前とは別。構え時間から光の長さを算出しない。ゲーム時計を使い休止/低速/ヒットストップと同期する。短い連携で前段の有効判定と次段の光が重なっても次の光を省略しない。
パリィ受付180ms・最終合図160msと光480msは別。初点灯で押す説明は禁止。射撃は発射時と接触時を区別し、特殊パリィは到達時に合わせる。跳ぶ合図を早く出しすぎると着地後に被弾するので、実際のジャンプ軌道で検証する。

## 4. 判断が変わる攻防を設計
距離で攻撃選択を変え、攻撃中に突然パターンを差し替えない。短い隙/長い隙、追従/固定、接近/回避を組み合わせる。背後反撃は毎回にせず、予告と再使用制限を設ける。HP増加だけで難しくしない。全攻撃を赤にするとパリィ主体の良さが薄れる。基準ボスは一種類の最終段のみ赤。
裏回り連打や遠距離資源待ちで成立する戦法を必ず試し、それを禁止するのではなくリスク/報酬を調整する。第二形態は覚えた技を生かし、追加段や攻め時で差を作る。

## 5. 成長機会と報酬を守る
通常弾と水を連携内で混ぜ、待つだけの育成を避ける。水頻度を減らす場合は成長回数も合わせて検討。遠距離パリィと近接パリィに同じBREAK報酬を与えない。ボスを追加する際は資源が最後まで入手できることを確認。新ボスごとにプレイヤーの受付/回避距離を勝手に変えない。

## 6. 実装の責務
- data.ts: 共通調整値。boss.ts: 現ボスの攻撃/選択。次ボスでは定義を別ファイルにして選択口を設ける（現状は未実装）。
- enemy-system/special-system: 共有判定。game-state/practice: 状態と開始/終了/再戦。
- telegraph/boss-view/scene-view: 描画。events→event-presenter→audio/effects: 演出。
- UIは命令のみ。DOM/Phaserからモデルを直接書き換えない。新しいタイマーには解除・リセット・停止条件を必ず用意。

## 7. 最小の検証セット
npm run checkを通す。段時刻順序・光の境界・160ms前の音に合わせたパリィ・赤の拒否と回避・方向固定・左右接触・弾の移動区間判定・1振り1命中・BREAK中断・形態移行清掃・死亡/再戦・休止復帰・回復完了と被弾同フレームを確認。
自動検証の後、ユーザーへ表で確認依頼: 種類が分かるか/いつ押すか分かるか/反動が気持ちよいか/成長機会があるか/回復の隙があるか/理不尽な被弾があるか。実機未検証を成功扱いしない。

## 8. 保存と変更管理
ChatGPT Workで編集、GitHubを正本として各版保存。変更前後を別コミットにし、README/CHANGELOG/AUDITへ理由と評価を記録。公開したソースとGitHubのツリー一致を確認。トークンや生成物を保存しない。復旧はGitHub取得→npm ci→npm run check→起動。ユーザーの評価を受けるまでは自動テストだけで完成と宣言しない。
